How it works

Authority is checked before the action runs.

Parmana sits between an AI agent's request and the system it would change. The agent proposes. Your rules decide. Only permitted actions are released.

The four stages

Every action follows the same path. A refusal at any stage stops the action, and the refusal is recorded too.

1. DeclaredYour institution writes its authority as explicit, versioned rules. Each rule names the action, its limits, and whether a person must approve it.
2. AuthorizedThe proposed action, with its exact parameters and amount, is checked against the rule. If no rule matches, it is refused.
3. ExecutedPermitted actions pass the enforcement boundary once. On supported paths, the gateway holds the connector credentials and the agent never does.
4. ProvenA signed record of the request, the decision, any approval and the release is kept. It can be verified later.

Human approval, per action

Some actions need a person. Parmana does not treat a role or a scope as approval. It asks for a signed approval for one specific action.

Bound to the action

An approval covers one action, on one resource, up to one amount. Changing any of these means a new approval.

Single use and expiring

An approval is used once and expires after 15 minutes by default, or up to 24 hours where the policy allows.

Signed by a registered approver

Only registered approvers can sign. Each approval is a signature the record keeps.

Rules change under review

Policies, approvers and connectors change only through a second person (maker checker), and each change is signed.

The agent never holds the keys

An agent that can reach a system with its own credentials can skip any check placed in front of it. Parmana avoids that on supported paths.

The gateway holds the connector credentials. The agent sends a request and receives an answer, never the key. The gateway releases each action only after checking its signed authorization, and only once.

This protects against an agent that holds other credentials. It does not protect against a system an agent can reach another way. See limitations.

What Parmana does not do

  • It does not read the text a model produces. Prompt injection, toxic output and data leakage in text need a guardrail. Parmana limits what an agent can do, not what it says.
  • It does not enforce at the network level. Only actions routed through the gateway are covered.
  • It does not approve by default. If no rule matches, the action is refused. Facts the agent declares cannot cause an approval on their own.
