Tutorial: let an AI agent act through Parmana#

Tutorials · Architecture: agent workflow · Transaction limits

Goal. An agent proposes and submits business actions. Parmana decides whether each one runs, against the policy in effect and a signed human approval. The agent can ask. It cannot approve, and it cannot make the server believe an approval it made up.

Verification.

  • The refusals and the approval path were checked by tutorial 120 (examples/tutorials/120-no-action-without-approval/run.ts), which passed in the examples runner. Its Part 3 cases are quoted below.
  • The agent pattern (an SDK caller that declares, then executes with an attached approval) was run as declare-then-execute.ts and governed-flow.ts. The approval cases, including the declared-without-approval refusal, were run as approval-cases.ts: A, B, C and D refused, E approved.
  • The Python example python/examples/10_llm_tool_call.py is in the repository. It was not run in this verification.

The agent's position#

An agent is a caller with an API key. Its key has a list of capabilities it may invoke, and a list of principals it may act for. Those lists are the only permissions it has. Parmana checks them on every request.

The agent can The agent cannot
Propose a business action, with its parameters and the policy it runs under. Approve the action. Approval needs a person's signature.
Attach an approval that a person signed and gave it. Sign an approval itself. The agent never holds an approver's private key.
Read the status and the record of its own transactions. Propose or approve a change to a policy. Those are human, maker-checker routes.
Call declare and execute for the capabilities its key allows. Invoke a capability its key does not allow, or act for a principal it is not allowed.

Step 1: give the agent a narrow key#

The operator issues a key for the agent, with the fewest capabilities it needs and no governance rights:

bash
# Generated by the operator. The raw key goes to the agent's secret store, once.
parmana-ops keys generate-api-key --caller-id invoice-agent --out-dir ./agent-keys \
  --allowed-capabilities test:fixture-execute --allowed-principal-ids demo

The parmana-ops bin printed nothing in the published 4.1.1 release. The fix is in the repository; until a release contains it, run the command through its file, as described in CLI. keys generate-api-key writes two files to the output directory, <caller>.key (the raw key, owner-only) and <caller>.entry.json (the PARMANA_API_KEYS entry, with only the hash). It prints the paths, and no secret. Verified.

Do not set credentialHolderType to USER for an agent. A service caller is refused on the human-only routes with NON_HUMAN_CALLER_DENIED (verified in tutorial 103).

Step 2: the agent asks for approval, outside Parmana#

The agent prepares the request: the vendor, the amount, the purpose, and the policy it runs under. It sends that to your review workflow, not to Parmana yet. A person reviews it there. The reason is that a declared transaction executes exactly as it was declared, and an approval cannot be added to it afterwards (see the warning below).

typescript
// The agent's plan. Shown to the approver. Not sent to Parmana.
const plan = {
  purpose: "Pay invoice INV-2026-100 to vendor V-100",
  vendorId: "vendor://payments",
  amount: 1000,
  currency: "USD",
  policy: { name: "vendor-payment", version: "2.1.0" },
};
await reviewQueue.submit(plan); // your workflow; the approver reads plan.purpose, plan.amount and plan.vendorId

Step 3: a person approves, outside Parmana#

The approver is a person. They review the plan in their own tool, and sign only if they agree. They sign on their own machine with their own key:

typescript
// On the approver's machine. The agent never runs this and never sees the key.
import { readFileSync } from "node:fs";
import { signApproval } from "@parmana/sdk";

const approval = signApproval({
  privateKeyPem: readFileSync("approver.private.pem", "utf8"),
  approverId: "finance-approver-1",
  keyId: "finance-approver-key-1",
  capability: "test:fixture-execute",
  resourceId: "vendor://payments", // the target the plan names
  maxAmount: 1000, // the amount the plan names
  ttlSeconds: 900,
});
// The approver hands this JSON back to the agent, through your workflow.

Step 4: the agent builds the transaction with the approval, and executes#

The approval goes into the transaction before it is declared or executed. The agent then declares and executes, or executes in one call:

typescript
import { randomUUID } from "node:crypto";
import { ParmanaClient, createBusinessTransaction } from "@parmana/sdk";

const agent = new ParmanaClient({ endpoint, apiKey: process.env.AGENT_KEY });

const request = createBusinessTransaction({
  businessTransactionId: randomUUID(),
  principalId: "demo",
  purpose: plan.purpose,
  action: "test:fixture-execute",
  target: plan.vendorId,
  parameters: { amount: plan.amount, currency: plan.currency },
  policy: { name: "vendor-payment", version: "2.1.0", schemaVersion: "1.0.0" },
  signals: {
    humanApproved: true,
    approvalArtifact: approval, // the person's signature, carried as data
    vendorVerified: true,
    invoiceVerified: true,
    paymentApproved: true,
    sufficientFunds: true,
    paymentAmount: plan.amount,
    riskScore: 5,
    vendorId: plan.vendorId,
  },
});

await agent.declareTransaction(request); // RECEIVED
const record = await agent.executeTransaction(request.businessTransactionId); // APPROVED
// or, in one call: const record = await agent.execute(request);

Parmana verifies the approval against the request: its signature, its scope, its amount, its target, its expiry, and whether it has been used. It does not take the agent's word.

Warning: a declared transaction is fixed. executeTransaction(id) runs the stored declared request. It does not take a new body, and an approval cannot be added to a request after it was declared. Verified: a transaction declared without an approval was refused when executed. The same request declared with the approval was approved. If an agent declares an unapproved request, that id is used: a later attempt with the approval is a 409, not a new decision. Declare only when the approval is in hand, or use the one-call execute.

What the agent sees in each case#

Tutorial 120 Part 3 ran these cases against a real execution path:

Case Result
The agent sets humanApproved: true and attaches no signed approval, with no approval verifier configured Refused: no approval verifier is configured, so the signed human approval cannot be checked.
The agent sets humanApproved: true with no signed approval, with the verifier configured Refused: the declared humanApproved is true, the verified one is false.
A person signs an approval, the agent attaches it Approved.

The first two cases are the reason an agent cannot approve itself. The server checks the approval; the agent's declaration is not enough.

Tutorial 120 Part 1 also shows that a policy cannot be written so that an agent's declarations approve an action. Each of these was refused at policy validation: an approve rule that always approves; an approve rule on facts the agent declares; an approval signal inside an any branch that another branch could satisfy alone; and an approval signal that is not declared in approvalSignals.

Make the agent's requests reviewable#

  • Give every request a purpose a person can read. The approver decides from it, and it is part of the record.
  • Keep one transaction id per action. The agent retries reads, not executions. See the Node.js tutorial for the outcomes.
  • Do not declare a request before its approval exists. A declared request is fixed (see the warning in step 4).
  • Set the amount and target from the agent's plan, and let the approver sign exactly that. An approval for another target or amount is refused.
  • Record the request and the record. A declared request is RECEIVED until it is executed; the record is the evidence after.

Production notes#

  • Do not give an agent a key that can invoke an action without a policy that requires a human approval. Check each capability's policy in Policy management.
  • An agent that calls a business system with its own credentials, outside Parmana, is outside the record. Make the target system accept only Parmana's connector.
  • Revoke an agent's key by changing its entry, through your configuration process, and check GET /callers/me after any change.
