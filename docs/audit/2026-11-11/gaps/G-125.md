## Exact entry text

**G-125. A retry after a lost response cannot recover the outcome of a mutating call.** The execution path consumes the authorization's nonce before the connector runs: `ExecutionGateway.verify()` consumes it at `packages/execution-gateway/src/ExecutionGateway.ts:619–623` when no `executionControl` is configured, and `packages/api/src/bootstrap/createReleaseVerifier.ts:66` consumes it when one is. Before Part 1, nothing recorded what the connector returned. Status: in progress. Part 1 (outcome record per nonce) is implemented and tested, but not yet applied to a database; Parts 2 and 3 are not started. Three consequences follow, each confirmed by reading the code path:

- **The connector ran, the response was lost.** The nonce is burned. A retry with the same authorization is refused with `NonceAlreadyConsumedError`, so the client cannot tell "executed" from "never executed," and parmana has no stored result to return.
- **A failure after consumption but before the connector runs** (capability resolution, session creation in `ExecutionControlService.execute()`, or the `session.created` audit write) burns the nonce with no effect. A legitimate retry is then refused.
- **The connector succeeded but the `execution.completed` audit write failed.** The effect happened and the nonce is consumed, with no completion record.

This is the same class as the unknown-outcome question raised in the public MCP discussion (modelcontextprotocol/modelcontextprotocol#3394), where a retry of a mutating `tools/call` re-executes external effects. Parmana's single-use nonce prevents double execution, which is correct, but it does not give the client a way to recover the result.

Plan (2026-10-27), in three parts:

1. **Outcome record per nonce, in this repository.** An `execution_outcomes` table keyed by nonce, with `in_flight` and `completed` states (`failed` is added with Part 3). The `in_flight` row is inserted after the nonce is consumed on the direct path, and before it on the `executionControl` path. The result is written after the connector call. A retry returns the stored result, or `OutcomeUnknownError` for an `in_flight` row. Both paths use the same store. **Implemented 2026-10-27; see the next section.**
2. **Provider idempotency keys.** Derive the key from the nonce and send it on every provider call that accepts one. `packages/execution-gateway/src/connector-execution/GatewayPaytmAdapter.ts:73` derives Paytm's `refId` from the order ID, not the nonce, and the Paytm connector notes it has no server-side idempotency of its own (`packages/connector-paytm/src/PaytmTypes.ts:150–157`). No idempotency support was found in the HubSpot, GitHub or Slack connectors. **Not started.**
3. **Reconciliation of stale `in_flight` rows.** A scheduled job marks rows older than the connector timeout as `needs_reconciliation`, asks the provider whether the effect exists, and writes `completed` or `failed`. **Not started.**

**What Part 1 covers, and what it does not (2026-10-27).**

- Covered: a completed connector call is recorded. A replay returns the recorded result, and the connector is not called again.
- Covered: a replay while the first attempt is in flight, or after it stopped without recording completion, is refused as `OutcomeUnknownError` (409, `OUTCOME_UNKNOWN`). The caller must check the external system before acting again.
- Not covered until Part 3: a failure before the connector runs on the `executionControl` path (session creation, or the `session.created` audit write) leaves the row `in_flight`, not `failed`. A retry is refused as unknown, not as failed.
- Not covered: if the completion write fails after a successful call, the caller gets that error and the row stays `in_flight`. The effect is not hidden, but the outcome is not recorded.
- Not covered: if the `execution.completed` audit write fails, the row stays `in_flight`. The audit is written before completion, so a failed audit leaves the outcome unrecorded.
- Not covered: a crash between the nonce consume and the `in_flight` insert on the direct path leaves a consumed nonce with no row. A retry is then refused as `NonceAlreadyConsumedError`, which the caller treats as unknown.
- Deployment: the production gateway needs migration `20261027120000_add_execution_outcomes.sql` applied first. Without it, the insert fails after the nonce is consumed, so the request fails and its nonce is burned.
- Verified: gateway unit tests, store unit tests with a fake pool, and the shipped migration run on PGlite (real PostgreSQL semantics). Not yet run against a hosted Supabase project.

Even with all three parts, a crash between a successful connector call and the completion write leaves the row `in_flight` until reconciliation runs. For connectors without an idempotency key, reconciliation depends on a stored provider object ID and is only as strong as that lookup. The gap narrows to that window and does not disappear.

Evidence: the code paths above; `docs/site/security/overview.mdx`; `docs/internal/CLAIMS.md` §2.8. Part 1 tests: `packages/execution-gateway/tests/unit/execution-gateway.test.ts` (`outcome recording (G-125)`), `packages/storage/tests/unit/postgres-execution-outcome-store.test.ts` (fake pool), and `packages/storage/tests/unit/postgres-execution-outcome-store.pglite.test.ts` (the shipped migration on PGlite).
