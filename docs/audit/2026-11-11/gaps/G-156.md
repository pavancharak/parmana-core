## Exact entry text

**G-156. The manifest's read or write label is not enforced, so a capability marked "read" can send a write.** In parmana-connect, `schema/manifest.schema.json` checks `method` and `effect` independently. `src/manifest.ts` (`semanticChecks`) rejects only `GET` combined with `effect: write`. So `effect: read` with `POST`, `PUT`, `PATCH` or `DELETE` is accepted. `src/connector.ts` (`createGenericConnector`) sends whatever method the manifest declares and never reads `effect`. parmana-core's `GatewayExternalAdapter` also never reads `effect`: it sends every release as a POST, so the approval gate is the only check that applies to reads and writes alike. Impact: a capability reviewed as read-only can change data on the business system once it is approved. Status: fixed in parmana-connect and merged to its main through PR #36 (commit 056e8ac). A test covers each refused combination. Issue #467 stays open until it is closed. Closing it needs a rule in `manifest.ts` that refuses `effect: read` with any method other than `GET`, and a test for each refused combination. Process: linked issue #467. Claim: CLAIMS 2.47 covers approval; this gap limits what the approval is shown to cover.
