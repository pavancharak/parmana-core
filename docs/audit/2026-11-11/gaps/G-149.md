## Exact entry text

**G-149. Authorizations with no signals hash skip the release-time signal and approval checks.** `ExecutionGateway.verify` runs the signal verifier only when the authorization carries a `signalsHash`. Without one, `signalsStillCurrent` stays undefined, and `priorChecksPassed` treats undefined as a pass. `RuntimeEngine.execute` now always signs a `signalsHash`, so only authorizations signed before that check existed are affected. Those authorizations passed the approval check at decision time, but nothing re-checks the approval at release. Status: closed. `ExecutionGateway.verify` refuses at release an authorization with no `signalsHash` when the signal state verifier is wired. The release check's result is `signalsStillCurrent: false`, so the request fails and nothing is executed. Before this, an absent check was a pass. RuntimeEngine signs a hash on every authorization it issues now, so only an authorization issued before that check existed is refused. Tests: `packages/execution-gateway/tests/unit/signal-freshness.test.ts` and `release-approvals.test.ts` (both updated to expect the refusal). Process: linked issue #453.

## Dated note, 2026-11-24

The entry above describes the state before this note, and its closure was limited: the refusal applied only when the signal verifier was wired. With no verifier, a release with a matching or absent hash could still proceed.

- **Refusal without a hash, always:** `ExecutionGateway.verify` now sets `signalsStillCurrent: false` for an authorization with no `signalsHash`, whether or not a verifier is wired.
- **Drift check without a verifier:** a present `signalsHash` is compared against the request's signals in every configuration. The verifier is consulted only for divergence from verified state.
- **Verifier required at construction:** the constructor throws unless a `signalStateVerifier` is supplied. Test fixtures that do not exercise signals set the named opt-out `allowUnverifiedSignals: true`. Production bootstrap (`packages/api/src/bootstrap/createExecutionGateway.ts`) already wires the verifier and does not set the opt-out.
- **Regression test:** `signal-freshness.test.ts` now includes a no-hash, no-verifier case with changed signals. It failed on the previous code, the reason the test was added.
- **Behaviour change for callers:** an authorization signed without signals is refused. The examples that relied on this were updated to sign over the hash of empty signals, or to pass the signals the authorization was decided on.

Verification on Node 24.22.3 at the commit that carries this note: `packages/execution-gateway`, `packages/runtime` and the non-database `packages/api` unit tests passed (1216 tests in 176 files); `npm run typecheck` passed; `npm run examples` completed with exit 0. Not run: the Postgres-backed storage and API integration suites, which need a running database and fail here with connection refused.

The opt-out still makes `signalsStillCurrent` "not run" when a hash matches and no verifier is wired. Only tests can reach that state.
