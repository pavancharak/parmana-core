## Exact entry text

**G-126. A loopback `http://` connector base URL was accepted in production.** `readConnectorBaseUrl` (`packages/api/src/bootstrap/readConnectorBaseUrl.ts`) read `HUBSPOT_BASE_URL`, `GITHUB_BASE_URL` and `SLACK_BASE_URL` and accepted `http://localhost`, `http://127.0.0.1` or `http://[::1]` in every environment. Its comment said a production override must use `https://`, but the code did not check the environment. A production deployment that set one of these to a loopback `http://` address would have sent the connector credential (a bearer token or an App key) in clear text to that address. The exposure is limited: these variables are set by the operator in the environment, not by an agent, so an agent cannot trigger it, and the Paytm connector was already HTTPS-only outside tests. Status: fixed 2026-10-27 (commit `2b00dc5`), merged to `main` in PR #169 on 2026-10-28; the deployment check below is still open. The loopback exception now applies only when `NODE_ENV` is `test`, where the hermetic mock-server seams run. Tests: `packages/api/tests/unit/bootstrap/read-connector-base-url.test.ts` (six cases). The three connector integration suites that use these seams still pass. Not checked: whether any live deployment sets one of these variables to a loopback address. Open, and needs someone with access to the hosted (Vercel) and self-hosted environments: confirm that `HUBSPOT_BASE_URL`, `GITHUB_BASE_URL` and `SLACK_BASE_URL` are unset or use `https://`, and record the result here. The gap stays open until that result is recorded. Process: no linked issue or ADR yet, and no ChallengeRecord, because the change fixes a defect and does not challenge an existing claim (RFC-0022). Claim: CLAIMS 3.26, item 1.
