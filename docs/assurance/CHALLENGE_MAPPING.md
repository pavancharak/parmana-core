# Challenge mapping: proposed attack classes against Parmana

**Status:** Draft for owner review. Not a decision record. Changes to phases, exit criteria or score policy need an entry in [ASSURANCE_DECISIONS.md](../ASSURANCE_DECISIONS.md).
**Owner:** Pavan Charak.
**Prepared:** 2026-11-22, on branch `claude/laughing-meitner-cqaxvi`.

## 1. What this document is and is not

The proposal that prompted this document listed about 90 challenge titles, grouped into eight test programmes. The mapping below is based on **the titles only**. The full challenge descriptions are not in this repository, and no description was read when this document was written.

So each row is a hypothesis with two parts:

- **Repository evidence.** What was checked in the code, with the search or file used. Keyword hits are a rough signal. A hit shows a surface may exist. It does not show the behaviour is correct.
- **Proposed invariant.** The property a test would check. Tests should assert refusal of a forged or manipulated input, not reproduce an exploit.

No row here is a confirmed vulnerability.

## 2. Scope classes

| Class                 | Meaning                                                                                                                                       |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| **Product**           | Parmana's own code makes or checks the claim. Parmana should test it.                                                                         |
| **Deployment**        | The control lives in infrastructure or CI that a deployer runs. Parmana can test the repository's own config, not the deployer's environment. |
| **Not applicable**    | No corresponding component exists in this repository. Record the reason. Do not write a test for a component that does not exist.             |
| **Needs description** | The title does not settle the scope. The full challenge description is needed first.                                                          |

## 3. Mapping table

Status key: **Covered** means an existing automated test was run and passed or killed mutants. **Surface** means the code exists and no targeted test was found. **No surface** means the search found nothing.

## 4. Items for owner decision

1. **Scope rule.** Should challenges classed as _Deployment_ be tracked in this repository at all, or only in the deployer's assurance? This document assumes they are tracked as repository config checks only.
2. **Committed Terraform variables.** `infra/parmana-prod-signing/prod.tfvars` is committed and contains an AWS account ID and a signing key ARN. These are identifiers, not credentials. The owner should decide whether that is acceptable for a public repository. No change has been made.
3. **Full challenge descriptions.** Several rows are _Needs description_. The descriptions should be supplied before any of them is turned into a test.
4. **Staging.** The proposal assumed an isolated staging environment. None is defined in this repository. The existing tests run in CI.
