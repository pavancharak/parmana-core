Parmana ships continuously, there's no separate server release train with its own version
numbers (the running server's `GET /version` reports an internal build identifier, not a
product version). The SDKs are versioned independently on their own registries, see
[TypeScript SDK](/sdks/typescript) and [Python SDK](/sdks/python) for their current versions
and per-version notes. This page covers changes that affect what you can build against, not
every commit, run `git log` in the repository for the complete record.

## 2026-10-12

**Listed: Parmana as a TRACE external evidence source in AgenTrust**

- [agentrust-io/integrations#294](https://github.com/agentrust-io/integrations/pull/294) was merged into the
  AgenTrust integrations repository. It adds `integrations/parmana-server`, which maps Parmana's signed records to
  TRACE references (`authorized-intent`, `approval-outcome`, refusals as their own unit), at tier `community` with no
  conformance level. A maintainer re-ran its tests and reproduced its output. It is a listing, not a certification;
  its fixtures come from the refund evaluation package, where connector results are mock results. CLAIMS.md 3.23.

**Added: Essays**

- A new [Essays](/essays/overview) tab explains Parmana end to end in plain language, from why it exists to what it
  does not do, including [Models as insider risks](/essays/models-as-insider-risks).

**Corrected: limitations and comparison pages**

- [Limitations](/security/limitations) no longer says no outcome goes unrecorded: a Refusal Record write fails open
  by design, so the refusal happens but its record can be missing (CLAIMS.md 3.11).
- [How Parmana compares](/how-parmana-compares) no longer says most teams require approval only above a risk
  threshold: every agent action needs a signed human approval (CLAIMS.md 2.47). It also notes that a policy can name
  a business signal source for a fact.

## 2026-10-11

**Added: live checks for authority grants, business signal sources and a real refund**

- [`examples/live-checks`](https://github.com/pavancharak/parmana/tree/main/examples/live-checks) gains three procedures for production. The `authority-grant` and `business-signal-source` checks passed in production the same day, all four requests each as required; the refund check is ready, not yet run:
  `authority-grant` (a grant decides: refused before it, approved within its limit, refused over it and after its
  revoke), `business-signal-source` (a deployed demo source answers, signed; the release carries its answer as a
  condition) and `paytm-refund` (one real 1 INR refund through the rotated credentials, its record verified offline).
- `examples/live-checks/governance.ts` runs the maker checker steps for policies, connectors, sources and grants with
  the SDK, showing each change and asking the checker to type `APPROVE` before signing the step up.

**Published: SDK 1.6.0 and connector SDK 0.3.0**

- `@parmana/sdk` and `parmana` 1.6.0 add the business signal source and authority grant methods, and `conditions`
  on `ParmanaRelease`. `@parmana/connector-sdk` 0.3.0 adds `ReleaseCondition`. `parmana-connector-sdk` is unchanged
  at 0.2.0.
- Published on npm and PyPI from the files of release
  [sdk-v1.6.0](https://github.com/pavancharak/parmana/releases/tag/sdk-v1.6.0), byte for byte: see
  [New in 1.6.0](/sdks/typescript#new-in-160).

**Added: re-check at release, and execute only if still valid**

- The authorization Parmana signs now carries what the decision rests on: the business facts with their `validUntil`,
  and the agent's authority grant. The gateway checks them again at release; if one no longer holds, nothing is sent
  and the request gets `409 AUTHORIZATION_NO_LONGER_VALID` with `executionStatus: NOT_EXECUTED`.
- A release to an external connector carries the facts as signed `conditions` and expires no later than the earliest
  one. An endpoint that finds one no longer holds answers `conditionsNotMet` and does not act. See
  [Connect any external system](/guides/connect-any-external-system).
- `502 EXECUTION_OUTCOME_UNKNOWN` now also says `executionStatus: EXECUTION_UNKNOWN`.
- The SDKs' `ParmanaRelease` type has `conditions`; the example endpoints take a `conditionsHold` check.

**Added: per-agent authority grants**

- Say which agent may have which action decided, within limits on each request (`min`, `max`, `oneOf` by Intent
  path), until when: `POST /authority-grants/changes`, approved by a second person with a step up authorization. No
  one grants authority to themselves. See [Grant an agent authority](/guides/grant-an-agent-authority).
- A policy opts in with `requireAuthorityGrant`. A request from a key with no grant in force, or outside its limits,
  is refused as `NOT_AUTHORIZED`; after the grant's expiry, as `AUTHORITY_EXPIRED`. The grant checked is in the
  signed record, under `assessment.authority.grant`.
- `GET /policies/in-effect` answers `authorityGrantRequired: true` for such a policy.
- Self managed deployments: apply the new migration with `npm run db:migrate -- apply` before deploying this version.
- No shipped policy requires a grant; decisions are otherwise unchanged.

**Added: any business system as a trusted signal source**

- Register a business system that owns facts a policy needs, an ERP, an order system, a CRM, a ledger, under a name,
  through maker checker: `POST /business-signal-sources/changes`, approved by a second person with a step up
  authorization. See [Connect a business signal source](/guides/connect-a-business-signal-source).
- Parmana asks it with a query signed by its default key, and, when the source is registered with an Ed25519 key,
  accepts only answers signed with that key. The Trusted Signal records `sourceProof`, `sourceKeyId` and
  `sourceProofVerified`. An answer Parmana cannot trust refuses the request as `SOURCE_UNAVAILABLE`.
- `typescript/examples/08-business-signal-source.ts` is a complete source endpoint.
- Self managed deployments: apply the new migration with `npm run db:migrate -- apply` before deploying this version.
- The SDK methods (`proposeBusinessSignalSourceChange()`, `business_signal_sources.propose_register()` and the rest)
  are in SDK 1.6.0.

## 2026-10-10

**Added: business validation, in the runtime**

- A policy can name the business system that owns a fact (`signalSources`). Parmana asks that system itself,
  never using the agent's value, records the answer as a Trusted Signal, and evaluates the policy on it. A
  proposed value that differs from the source's is refused. See [Business validation](/concepts/business-validation).
- Every decision now carries `assessment`: authority, business validation and, for a refusal, execution, as
  separate statuses, signed inside the Execution Trust Record and the Refusal Record. Records written before
  this change have no `assessment` and still verify.
- `GET /policies/in-effect` lists a policy's sourced facts under `signals.sourced`, when it has any.
- No business system is registered in the server yet, so a policy that declares one is refused as
  `SOURCE_UNAVAILABLE`. No shipped policy declares one; decisions are otherwise unchanged.

## 2026-10-06

- A Refusal Record now carries `policyContentHash`, the SHA-256 hash of the policy content that decided the refusal,
  inside the signed record. It is the same value an Execution Trust Record carries in
  `transaction.policy.contentHash`, so a refusal and an approval under the same policy can be matched. See
  [Refusal Records](/concepts/refusal-records).

**Fixed: an incomplete request body is a `400`, not a `500`**

- A `POST /execute` or `POST /transactions` body without `metadata`, `authority`, `authorization`, `intent` or
  `policy`, or with one of them `null` or of the wrong type, or a required field that is not a string, is refused
  with `400` naming it (G-87). Before, a missing `policy` or `authorization` was a bare `500`. Nothing was executed
  either way. See [Error handling](/api-reference/error-handling).

**Changed: a release tries the next checked address**

- A release to an external connector whose first resolved address refuses the connection now tries the endpoint's
  other checked addresses, under one timeout (G-83). Once a connection is made nothing is retried, so the endpoint
  never receives a release twice.

**Added: fuzz tests**

- Property based tests of the request boundary, policy loading and evaluation, the offline verifier and approval
  parsing run with every `npm test`. Besides G-87 they found that the policy validator threw a `TypeError` on fields
  of the wrong type (G-90) and that the offline verifier threw on malformed hybrid signatures (G-91). Both now refuse
  with a clear error.

**Added: every open issue in one place**

- [Limitations](/security/limitations#open-issues) lists every gap still open and what to do meanwhile; the same
  list, with evidence, is under "Open issues at a glance" in `docs/VERIFICATION-GAPS.md`.

## 2026-10-05

**Changed: a request whose signals do not have the declared types is refused**

- Every signal a policy declares in `signalsSchema` must now have that type (`boolean`, `number`
  or `string`) before any rule runs. A mismatch, such as an amount sent as `"500"`, is refused
  with `matchedRuleId` `signal-type-violation` and a reason naming the signal. Signals the
  policy does not declare, and signals not sent, are not affected. A policy whose
  `signalsSchema` uses any other type no longer validates.

**Changed: a partially chained Execution fails the execution chain check**

- Verifying an Execution Trust Record now fails when an `Execution` carries only some of its
  chain fields (`chainHash`, `chainSignature`, `previousChainHash`), or has none after a chained
  one. Before, such an `Execution` was skipped as data from before chaining, so an edited one with
  its `chainSignature` removed passed the chain check; the record's own signature still caught
  the edit. Records the runtime writes are unaffected: it always writes both fields together.
  `docs/VERIFICATION-GAPS.md` G-89.

**Added: mutation testing of the security packages**

- `npm run mutation -- <package>` measures how many deliberate changes to the security code the
  tests catch. First scores: `envelope-verifier` 89.7%, `approval` 77.7%, `policy` 50.3%,
  `execution-gateway` 67.6%, `crypto` 65.4% (on Node 22, which skips the ML-DSA-65 tests; the
  command now needs Node 24). Re-run on Node 24 after the fixes: `envelope-verifier` 94.0%,
  `approval` 93.9%, `policy` 96.0%, `crypto` 85.0%, `execution-gateway` 83.6%. The gaps that
  matter for security now have tests; see
  [docs/MUTATION-TESTING.md](https://github.com/pavancharak/parmana/blob/main/docs/MUTATION-TESTING.md).

**Added: an SBOM with every SDK release**

- From the next release on, each SDK package on a
  [GitHub release](https://github.com/pavancharak/parmana/releases) has a CycloneDX SBOM beside it
  (`<package file>.cdx.json`), covered by the signed provenance. See
  [Verifying an SDK package](/security/overview#verifying-an-sdk-package-from-a-github-release).

**Added: verify a record in your browser**

- [Verify a record in your browser](/verification/verify-in-browser) checks a signed Execution
  Trust Record's hash and Ed25519 signature with Web Crypto, in the reader's browser. It comes
  with an example record and a changed copy that fails, and can fetch the sandbox's public key.
  A test runs the page's code against records signed by Parmana's signer.

**Added: a threat model**

  attackers, and for each of 17 threats the control, the evidence (an attack scenario or a

**Fixed: security and correctness issues from an internal review**

These change behavior a caller or operator can see
([pavancharak/parmana#6](https://github.com/pavancharak/parmana/pull/6),
[pavancharak/parmana#7](https://github.com/pavancharak/parmana/pull/7),
[pavancharak/parmana#8](https://github.com/pavancharak/parmana/pull/8)):

- A rejected or already approved policy change can no longer be approved and applied
  (`409`). Two approvals of the same change at once apply it only once; a retry by the same
  approver after a partial failure completes. New migration
  `20261003120000_unique_policy_change_approval_per_pending_change.sql`.
- `POST /execute` refuses a `metadata.tenantId` the API key does not list in its new
  `allowedTenantIds` (`403 TENANT_NOT_ALLOWED`). A request with no tenant id is unaffected.
- A signed approval's `scope.field` is checked: `value` when the policy declares a `value`,
  otherwise `resourceId`. The SDKs and `scripts/sign-approval.ts` already write these.
- The gateway checks a request with no `signals` against the authorization's signed signals
  hash instead of skipping the check.
- Failed authentication is rate limited per IP (`RATE_LIMIT_AUTH_FAILURE_PER_MINUTE`, default
  30), and key discovery shares the public rate limiter.
- `page` and `pageSize` on `GET /transactions` and `GET /trust-records` must be whole numbers;
  `pageSize` is at most 100 (`400` otherwise).
- Under AWS KMS: `GET /.well-known/jwks.json` lists the signing keys instead of answering `501`;
  a key ARN is refused as a key id; public keys are cached for 5 minutes; a tenant key
  `tenant.<id>` maps to the alias `alias/tenant/<id>`.
- The server refuses to start with `CRYPTO_MODE=hybrid` and `KEY_PROVIDER=aws-kms`, or with
  hybrid key files missing.
- GitHub targets accept only a valid `owner/repo#number`.

**Changed: the TypeScript and Python SDKs are proprietary**

- From the next release, `@parmana/sdk` and `parmana` are licensed under the same proprietary,
  evaluation only license as the rest of the repository, replacing the Apache License 2.0.
  Versions already published keep the license they were published under. `@parmana/sign`
  stays under the Apache License 2.0.

**Moved: the repository is now github.com/pavancharak/parmana**

  [`pavancharak/parmana`](https://github.com/pavancharak/parmana), with its full history. Every

## 2026-10-02

**Fixed: canonical JSON keeps `"__proto__"` keys**

- The server's canonical serializer and the TypeScript SDK's `canonicalSerialize` silently
  dropped an object key named `"__proto__"`, so its content was not covered by the hash or
  signature. Both now keep it, matching the Python SDK and `@parmana/sign`. Output for data
  without that key is unchanged, so existing signatures stay valid.

**Sandbox: visitor data deleted, retention paused**

- Every request and record visitors had sent to the public sandbox was deleted around 03:30 UTC, around the
  retention job's first run. Production was not affected. The job is paused. Sandbox records are not guaranteed to
  be kept: keep any record you need.
- The retention function now refuses any period under 7 days without an explicit confirmation word, and logs every
  run that deletes.

**Added: sandbox retention**

- A daily job in the sandbox database deletes every request and record visitors sent more than 7 days ago, and keeps
  the sandbox's policy, approver and registration. Sandbox only: it is not a migration, and it refuses any database
  without the sandbox's registration.

**Added: the public sandbox and the Playground (ADR-0014 steps 2 to 4)**

- The sandbox is live at `https://parmana-sandbox.vercel.app`: the same code as production, its own database, signing
  keys and demo approver, one action (`sandbox:receipt`) released to an endpoint that acts on nothing. Its live check
  passed all nine checks on 2026-10-02.
- A published demo key, `2VfYWCzt_cBAPK-8uufX6ordfY2JuQhFPsohuEumKME` (caller `sandbox-visitor`, allowed only `sandbox:receipt`).
- New [Playground](/playground) page: the whole flow in cURL, PowerShell, TypeScript and Python, each run against the
  sandbox before publishing, with every real response and every refusal.
- Every **Try it** panel in the REST API tab now calls the sandbox first, with the demo key filled in. Production is
  still listed as a server.
- The [Quickstart](/quickstart) starts with two requests to the sandbox, and [Integrate Parmana](/agents/integrate)
  says how an agent practises there.
- Known issue, Python SDK 1.4.0: `verify_execution_trust_record_offline` reports a hash mismatch when given the decoded
  model of a record whose `previousChainHash` is `null`. Pass the record as plain JSON instead; the TypeScript SDK is
  not affected. Fixed in the repository the same day for the next Python release: a decoded model keeps the server's
  JSON and encodes back to exactly it, which also fixes sending a decoded refusal record or Execution Intent back for
  verification.

**Added: a registered external connector receives releases (ADR-0013 step 4)**

- An approved request for a capability registered as an external connector is released to the
  registered endpoint as a signed release: audience the endpoint URL, a 60 second expiry, the
  authorization id, the policy and the approvers, signed with the key at `GET /keys/default`. The
  endpoint's address is checked again at every release, and redirects are not followed.
- The registration's policy is the binding: a request must declare it at the version approved
  through policy governance, and `GET /policies/in-effect?capability=` answers for the capability.
  Every request is refused while no version of that policy is approved.
- Checked live in production on 2026-10-01 against a deployed endpoint: refused with no approval,
  released and recorded with one, refused when the approval was reused (`docs/CLAIMS.md` 2.50). The
  SDK helpers `verifyParmanaRelease` and `verify_parmana_release` are not published yet.
- Found in the live check: an approved request took 24 to 32 seconds in production, longer than the
  SDKs' default 30 second timeout (`docs/VERIFICATION-GAPS.md` G-84). After a timeout, read the
  record before sending anything new.
- **Examples:** an endpoint in TypeScript (`typescript/examples/07-external-connector-endpoint.ts`)
  and in Python (`python/examples/13_external_connector_endpoint.py`), each checking releases with
  its SDK helper, and Tutorial 123, which registers the TypeScript one through maker checker and
  releases to it. The API reference shows real responses for every refusal of the
  `/external-connectors` routes.

## 2026-09-30

**Added: external connectors, first step (ADR-0013)**

The goal: connect a new external system to Parmana with no change to Parmana's code. An operator
registers a capability to an HTTPS endpoint they run, and Parmana releases each approved request
there as a signed release. Built in steps; only the first is live.

- **Live in production: registering an external connector** through maker checker, like approver
  keys. One human caller proposes at `POST /external-connectors/changes` (a capability, the
  endpoint, the policy that governs it, the parameters Parmana may forward, a timeout); a
  different human caller approves with a step up signature. `GET /external-connectors` lists
  every registration. Refused: a capability in a built in connector's namespace, and an endpoint

**Added**

- **Execution Intents.** Before an action is released to a connector, the runtime now signs and stores a record of
  exactly what it is about to release. If that cannot be done, nothing is released and the caller gets
  `503 EXECUTION_INTENT_UNAVAILABLE`. This closes the ordering gap recorded as G-52 and makes the missing record
  recorded as G-53 repairable. See [Execution Intents](/concepts/execution-intents).
- Four routes: `POST /execution-intents/verify` (no credential needed), `GET /execution-intents/{businessTransactionId}`,
  `GET /execution-intents/unfinalized` and `POST /execution-intents/{businessTransactionId}/finalize`. The last two need a
  credential provisioned as a verified human. Finalize rebuilds a missing Execution Trust Record for a released action
  without calling the connector, and is safe to run twice.
- A fifth route, `POST /execution-intents/{businessTransactionId}/resolve`, lets a verified human close an intent in state `PREPARED` or `ERRORED` after reconciling it at the connector. It records what they found (`NOT_EXECUTED` or `EXECUTED`), a required note, who did it and when, and takes the intent out of the unfinalized list. It is idempotent and never calls a connector. The resolution is an attributed operator statement in unsigned status. It is not tamper evident and it is not a Trust Record.

- Signing a full Execution Trust Record under AWS KMS failed with `Member must have length less than

  verifiers accept it. Signatures issued before this change are unaffected. A verifier you wrote
  yourself must implement the same rule to verify large KMS signed records, see the

  verifier) imports. It is an optional extra, `pip install "parmana[verify]"`, and is included in the `dev`
  extra. It was previously imported but undeclared, which made the `Python SDK` CI check fail on `mypy`.
- The runtime now proves the evidence signing path works before it releases an action. If signing
  is unhealthy the request is refused with `503 SIGNING_UNAVAILABLE` and nothing is executed. If the
  action was released and the signed record then cannot be produced or persisted, the response is
  `500 EXECUTION_RECORD_INCOMPLETE` with the `businessTransactionId` and `authorizationId`, and you must
  reconcile instead of retrying as a new transaction. Enforced everywhere except `NODE_ENV` `test` and
  `development`. The startup log gains `signingReadinessConfigured`. This mitigates the ordering gap G-52
  and does not close it.

Adds `npm run verify:kms` (`scripts/verify-kms-signing.ts`), which signs test data through the repository's own `KmsSigner` on both sides of the 4096 byte KMS limit and requires KMS to refuse a raw message over it. Verified on 2026-09-20 against the real key with a limited IAM user, and end to end with the server signing a full Trust Record under KMS. Pages that said KMS was roadmap or not built (Cryptography, FAQ, Local deployment, Deploy patterns) are corrected. Azure Key Vault, Google Cloud KMS and HSM remain unimplemented.
- An approved action whose connector is not configured now returns `503` with code `CONNECTOR_NOT_REGISTERED` and the message `No connector is registered for capability '<action>' on this deployment. Nothing was executed.` Before, it was a bare `500` with no code, and only the server log named the cause. Both SDKs already expose the code (`serverCode` in TypeScript, `server_code` in Python 1.1.6).
- Deployment artifacts found by following the production runbook on a fresh clone. The `Dockerfile` copied a package that no longer exists (`packages/receipt`) and skipped real workspaces, and the image did not contain `docs/site/parmana-handbook.pdf`, which the API needs at startup, so a container built from it could not have started. `scripts/apply-all-migrations.sql` was missing 7 of 30 migrations (including `execution_audit_events` and `policies`) and carried outdated text for others. TypeScript: the client builds a default `HttpTransport` from its own configuration when `transport` is omitted, so `timeout`, `retryPolicy` and `apiKey` apply with no extra wiring (1.1.5 and earlier threw `Transport is required.`), and `userAgent` is now sent as the `User-Agent` header. Python: `InternalServerError` now carries the server's code on `server_code`, so you can tell `SIGNING_UNAVAILABLE` from `EXECUTION_RECORD_INCOMPLETE`. The Python client docstring now lists 429 among retried statuses.
- TypeScript SDK 1.1.3 (published to npm on 2026-09-20): `InternalServerError` now carries the
