---
title: "Credential setup runbook"
description: "Create, validate, grant and rotate every credential Parmana uses: caller API keys, step-up keys, approver keys and kill-switch keys, with the commands for each."
---

This runbook sets up every credential from scratch and says how to change what each one may do. It assumes the [maker-checker guide](/guides/credentials-maker-checker-approver) for the reasons behind the roles, and the [command reference](/cli/reference) for every flag.

## 1. The credentials

| Credential        | Held by                | Purpose                                 | Stored as                                      |
| ----------------- | ---------------------- | --------------------------------------- | ---------------------------------------------- |
| Caller API key    | a program or a person  | sends requests to the API               | a SHA-256 hash in `PARMANA_API_KEYS`           |
| Step-up key pair  | a checker              | signs a checker's approval of a change  | the public key in the caller's entry           |
| Approver key pair | an approver            | signs human approvals of actions        | the public key in the approver list            |
| Kill-switch key   | an operator or a probe | trips, resets or probes the kill switch | a caller API key with a kill-switch capability |

A caller API key is not an approver key. The caller key decides who may send a request. The approver key decides who may approve an action. Both checks apply.

## 2. Roles and rules

- **Each person generates their own credentials, on their own machine.** Nobody generates a credential for someone else, and nobody sends a private key or a raw key anywhere.
- **The maker and the checker must be different people.** The server refuses an approval from the caller that proposed the change.
- **Only public keys leave the machine that made them.** That covers the entry JSON and the `.public.pem` file. Raw keys, `.private.pem` files and step-up private keys stay put.
- **A raw key is shown once.** It's written to a file. Move it to a password manager, then delete the file.

## 3. Install the CLI from this repository

The published `@parmana/cli` does not include the `keys` commands yet. Build and link it from the repository. Do this once per machine, and again after switching branches.

```powershell
cd <repository folder>
git checkout main
git pull
npx tsc -b
npm link -w @parmana/cli
parmana-ops --help
```

Do not install with `npm install -g` from a folder. That pulls the published `@parmana/crypto`, which doesn't have the key functions.

Check the key commands are there:

```powershell
parmana-ops keys generate-api-key --help
parmana-ops keys generate-approver-key --help
```

## 4. Generate caller API keys

Each command writes owner-only files into `--out-dir`, and it prints paths, never secrets.

**Maker (`pavancharak`), on the maker's machine:**

```powershell
parmana-ops keys generate-api-key --caller-id pavancharak --out-dir "$env:USERPROFILE\parmana-keys" --credential-holder-type USER
```

**Checker (`mamta-checker`), on the checker's machine.** The checker needs an API key and a step-up key pair:

```powershell
parmana-ops keys generate-api-key --caller-id mamta-checker --out-dir "$env:USERPROFILE\parmana-keys" --credential-holder-type USER --generate-step-up-key
```

**Agent, scoped to the capabilities it needs (no `--credential-holder-type`, because an agent is not a person):**

```powershell
parmana-ops keys generate-api-key --caller-id refund-agent --out-dir "$env:USERPROFILE\parmana-keys" --allowed-capabilities razorpay:refund
```

**Kill-switch probe:**

```powershell
parmana-ops keys generate-api-key --caller-id kill-switch-probe --out-dir "$env:USERPROFILE\parmana-keys" --allowed-capabilities kill-switch:probe
```

The flags:

| Flag                              | Meaning                                                                                                                                                    |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--caller-id <id>`                | The name of the caller. It becomes the file name, so use letters, digits, `.`, `_` and `-` only.                                                           |
| `--out-dir <dir>`                 | Where the files go. Created if missing.                                                                                                                    |
| `--allowed-capabilities a,b`      | Actions this key may request. Empty means the key may request nothing. `*` allows everything, and should be used only for a deliberate, documented reason. |
| `--allowed-principal-ids a,b`     | Principals this key may act for. Without it, the key may act only as itself.                                                                               |
| `--credential-holder-type <type>` | Who holds the credential. Use `USER` for a person. Required with `--generate-step-up-key`.                                                                 |
| `--generate-step-up-key`          | Also creates a step-up key pair. Requires `USER`.                                                                                                          |

### The files each command writes

| File                           | Secret | Who keeps it                                            | Who receives it |
| ------------------------------ | ------ | ------------------------------------------------------- | --------------- |
| `<caller>.key`                 | yes    | the holder, in a password manager, then delete the file | nobody          |
| `<caller>.entry.json`          | no     | the holder                                              | the operator    |
| `<caller>.step-up.private.pem` | yes    | the checker only                                        | nobody          |

## 5. Generate approver key pairs

The approver generates the pair on their own machine:

```powershell
parmana-ops keys generate-approver-key --approver-id mamta-checker --key-id mamta-checker-key-1 --out-dir "$env:USERPROFILE\parmana-approver"
```

| File                                             | Secret | Who keeps it      | Who receives it |
| ------------------------------------------------ | ------ | ----------------- | --------------- |
| `mamta-checker__mamta-checker-key-1.private.pem` | yes    | the approver only | nobody          |
| `mamta-checker__mamta-checker-key-1.public.pem`  | no     | the approver      | the operator    |

The IDs may use letters, digits, `.`, `_` and `-` only. A key ID can't be reused for the same approver. Use `-key-1`, `-key-2` and so on, one per key.

## 6. Build the server list and deploy it

The operator collects every `*.entry.json` file and merges them into one JSON array. The server reads it from the `PARMANA_API_KEYS` environment variable, which holds only hashes.

```powershell
$entries = Get-ChildItem "$env:USERPROFILE\parmana-entries\*.json" | ForEach-Object { Get-Content $_.FullName -Raw | ConvertFrom-Json }
$value = ConvertTo-Json -InputObject @($entries) -Depth 6 -Compress
$value
```

Check the list before you save it. Each entry should have one `callerId`, a 64-character `keyHash`, and the capabilities you intended. Then:

1. In Vercel, open the project for the live API. Go to **Settings, Environment Variables**.
2. Edit `PARMANA_API_KEYS`, replace its value with `$value`, and mark it as a secret.
3. Redeploy. The new value takes effect only in a new deployment.

Keep the entry files. A host usually can't show a secret back, so these files are the only readable copy of the list.

## 7. Validate each credential

After the redeploy, test every key with its own raw key. Set the key for the session, never in a file:

```powershell
$env:KEY = "<raw key>"
curl.exe -s -H "Authorization: Bearer $env:KEY" https://your-parmana-server/callers/me
```

The response shows the caller's `callerId`, `allowedPrincipalIds` and `allowedCapabilities`. Compare them with what you intended.

| Result                                      | Meaning                                                             | Action                                 |
| ------------------------------------------- | ------------------------------------------------------------------- | -------------------------------------- |
| `200` with the expected `callerId`          | the key works                                                       | none                                   |
| `401`                                       | the key is not in the deployed list, or the deploy has not finished | check the list and the deploy          |
| `200` with fewer capabilities than intended | the entry is missing a capability                                   | fix the entry (section 8) and redeploy |
| a retired key returns `200`                 | the old key was not removed                                         | remove its entry and redeploy          |

For the kill-switch probe, check the status route, then send one probe:

```powershell
curl.exe -s -H "Authorization: Bearer $env:KEY" https://your-parmana-server/kill-switch/status
'{"status":200}' | Set-Content probe.json -Encoding ascii
curl.exe -s -X POST -H "Authorization: Bearer $env:KEY" -H "Content-Type: application/json" -d "@probe.json" https://your-parmana-server/kill-switch/probes
Remove-Item probe.json
```

`200` for status and `201` for the probe mean it works. The probe writes one record to the database, so send it once. A key without `kill-switch:probe` should get `403` with `CAPABILITY_NOT_ALLOWED`.

For the approver's public key, the first line must be the public header:

```powershell
Get-Content "$env:USERPROFILE\parmana-approver\mamta-checker__mamta-checker-key-1.public.pem" -First 1
```

It must read `-----BEGIN PUBLIC KEY-----`. A `PRIVATE KEY` header means the wrong file was sent. Stop, and treat that key as exposed.

## 8. How to add or change capabilities

Capabilities control what a key may do. They work differently for callers and approvers. Each has its own route.

### Caller keys: add a capability to an existing key

The raw key does not change, so the holder keeps using it. You change only the entry, then redeploy.

1. Open the entry file, for example `refund-agent.entry.json`.
2. Add the capability to `allowedCapabilities`, using the exact action name.
3. Rebuild `PARMANA_API_KEYS` (section 6) and redeploy.
4. Validate with `GET /callers/me`. The new capability should appear.

The PowerShell edit:

```powershell
$path = "$env:USERPROFILE\parmana-entries\refund-agent.json"
$e = Get-Content $path -Raw | ConvertFrom-Json
$e.allowedCapabilities = @(@($e.allowedCapabilities) + "razorpay:refund-fetch" | Select-Object -Unique)
$e | ConvertTo-Json -Depth 6 | Set-Content $path -Encoding ascii
Get-Content $path
```

Replace `razorpay:refund-fetch` with the capability you're adding. Use the same spelling the code uses for the action.

To remove a capability, use the same edit with `Where-Object { $_ -ne "<capability>" }` in place of the addition.

### Caller keys: create a new key with capabilities

Generate a new key with `--allowed-capabilities`, as in section 4, then deploy its entry. Retire the old entry when the new key is validated.

Use a new key when the old key may have leaked, or when the holder changes. Otherwise, edit the entry.

### Approver keys: changing capabilities

The server won't re-add an existing approver key. It answers `Approver '<id>' key '<key>' already exists. Use a new key id to add a new key.` So changing an approver's capabilities means a new key ID.

1. The approver generates a new pair with a new key ID, for example `mamta-checker-key-2` (section 5).
2. The maker proposes the new key with the capabilities it should have:

   ```powershell
   parmana-ops approver propose-add --approver mamta-checker --key mamta-checker-key-2 --public-key-file mamta-checker__mamta-checker-key-2.public.pem --capabilities razorpay:refund,hubspot:deal-update --reason "<why>" --dry-run
   ```

   Run it again without `--dry-run` once the dry run shows `BEGIN PUBLIC KEY`.

3. The checker approves the change (section 9).
4. Once the new key is active and tested, the maker proposes revoking the old key, and the checker approves that too:

   ```powershell
   parmana-ops approver propose-revoke --approver mamta-checker --key mamta-checker-key-1 --reason "<why>"
   ```

Each approver key carries its own capabilities. Revoking the old key does not affect the new one.

### Which names to use

Capability names must match the action name exactly. Examples used in this codebase:

| Capability              | Used for                                                                |
| ----------------------- | ----------------------------------------------------------------------- |
| `razorpay:refund`       | refund actions in the sandbox                                           |
| `razorpay:refund-fetch` | reading refund details                                                  |
| `paytm:refund`          | refund actions through Paytm                                            |
| `hubspot:deal-update`   | updating a HubSpot deal                                                 |
| `github:pr-merge`       | merging a GitHub pull request                                           |
| `erp:invoice-pay`       | paying an ERP invoice                                                   |
| `erp:record-update`     | updating an ERP record                                                  |
| `sandbox:receipt`       | sandbox receipts                                                        |
| `kill-switch:probe`     | recording a kill-switch probe                                           |
| `kill-switch:trip`      | turning the kill switch on                                              |
| `kill-switch:reset`     | turning the kill switch off; a reset needs a second, different operator |

Check the list against the actions your policies actually use before granting a capability. A capability that matches no action grants nothing.

## 9. Maker-checker for approver keys

The maker proposes, a different checker approves with a step-up signature, and the change takes effect for the next request.

**Maker:**

```powershell
parmana-ops approver propose-add --approver mamta-checker --key mamta-checker-key-1 --public-key-file mamta-checker__mamta-checker-key-1.public.pem --capabilities razorpay:refund --reason "<why>"
```

**Checker, on the checker's machine:**

```powershell
parmana-ops approver list --status PENDING_APPROVAL
parmana-ops approval sign --key-file "$env:USERPROFILE\parmana-checker\mamta-checker.step-up.private.pem" --key-id mamta-checker --pending <change-id> --action approve --out envelope.json
parmana-ops approver submit --change <change-id> --action approve --envelope envelope.json --dry-run
parmana-ops approver submit --change <change-id> --action approve --envelope envelope.json
```

**Anyone, to confirm:**

```powershell
parmana-ops approver list --status APPROVED
```

Rules:

- Sign and submit within 120 seconds. The envelope works once.
- Sign with the step-up private key, not the approver key.
- To reject, use `--action reject` with a `--reason`.

## 10. Rotate and retire

| To                     | Do                                                                                                         |
| ---------------------- | ---------------------------------------------------------------------------------------------------------- |
| rotate a caller key    | generate a new key with the same flags, deploy its entry, validate, then remove the old entry and redeploy |
| retire a caller        | delete its entry, rebuild the list, redeploy                                                               |
| rotate a step-up key   | generate a new checker key pair, deploy its public key, validate, then retire the old one                  |
| retire an approver key | propose a revoke, and approve it (section 8)                                                               |

Rotate a key at once if it was pasted into a chat, a ticket or a log. Change related values together, then redeploy both sides. A request that falls between two half-done changes fails.

## 11. Troubleshooting

| Symptom                                                         | Cause                                                    | Fix                                                                    |
| --------------------------------------------------------------- | -------------------------------------------------------- | ---------------------------------------------------------------------- |
| `Refusing to overwrite an existing file`                        | the output folder already has that file                  | choose another `--out-dir`, or move the old file aside                 |
| `--caller-id must use only letters, digits, ".", "_" and "-"`   | the name is not a safe file name                         | pick a simpler name                                                    |
| `--generate-step-up-key requires --credential-holder-type USER` | a step-up key was requested for a non-person             | add `--credential-holder-type USER`                                    |
| `is a public key. Sign with the private key`                    | `approval sign` was given the public PEM                 | use the step-up private PEM                                            |
| `is not a readable private key in PEM format`                   | the key file is damaged or not PEM                       | generate a new pair; do not edit the file                              |
| `--reason is required to reject`                                | `approver submit --action reject` without a reason       | add `--reason "<why>"`                                                 |
| `Approver '<id>' key '<key>' already exists`                    | the approver key ID is already used                      | use a new key ID                                                       |
| `CAPABILITY_NOT_ALLOWED` (403)                                  | the key lacks the capability                             | add it to the entry, then redeploy (section 8)                         |
| `SameActorCannotApproveOwnChangeError`                          | the checker used the maker's key                         | approve with the checker's own key                                     |
| `NON_HUMAN_CALLER_DENIED`                                       | a governance route was called with a non-person key      | create the key with `--credential-holder-type USER`                    |
| `PARMANA_TOKEN` not set, or 401                                 | the token is missing or not in the deployed list         | set `$env:PARMANA_TOKEN` to your own raw key; check with `/callers/me` |
| envelope expired or already used                                | more than 120 seconds passed, or it was submitted before | sign again and submit within 120 seconds                               |
| `authentication required`                                       | the key is not in the deployed list                      | check section 7 and redeploy                                           |
| `ERR_MODULE_NOT_FOUND`                                          | the repository is not built                              | run `npx tsc -b`                                                       |
| the key commands are missing                                    | the CLI on this machine is the published one             | run section 3                                                          |
| the server does not start after a change                        | `PARMANA_API_KEYS` is not one valid JSON array           | rebuild the list from the entry files                                  |
