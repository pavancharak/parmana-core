# Test account run: secondary key secret and server-role read (2026-11-21)

**Status:** the steps below ran and produced the results recorded in §6. Cleanup in §9 is **pending**. Production was not changed by this run. Nothing here is a production sign-off.

This page is the complete record of the run. A later reader should be able to repeat it from §10 and check the results against §6.

---

## 1. Purpose

Check, in a separate AWS test account, that:

1. The Terraform stack in `infra/parmana-test-signing` creates the secondary-key secret and its policies.
2. The server role, `parmana-test-server`, can read that secret.
3. The stored key is an ML-DSA-65 (dilithium3) private key, the type the startup check requires.
4. The stored key was generated by a known tool, so its origin is known.

**Out of scope:** production, the full API server startup, KMS signing with the test key, and CloudTrail alerting.

## 5. Procedure, as executed

### 5.1 Test account and budget

1. A standalone AWS account was created with a new email address.
2. A monthly cost budget of USD 10 was created with an alert at 80%.
3. The root user was used only for setup. MFA was enabled on root.

### 5.2 Test runner identity

1. IAM user `parmana-test-runner` was created with no console access.
2. The policy in §3 was attached to it.
3. One access key was created and saved on the operator's PC.

### 5.3 Identity check

The first run of `scripts/aws-identity-check.py` failed with HTTP 403, `SignatureDoesNotMatch`, "Credential should be scoped to a valid region". The script signed STS requests for the region in `AWS_REGION`. STS is global and accepts only `us-east-1` signatures. The fix (commit `2897eea4`) always signs for `us-east-1`.

The second run printed:

```
Account: 703759331191
Arn: arn:aws:iam::703759331191:user/parmana-test-runner
```

### 5.4 Test signing key

```powershell
.\infra\parmana-prod-signing\create-signing-key.ps1 -Environment test -Region ap-southeast-2
```

Output: `arn:aws:kms:ap-southeast-2:703759331191:key/f56e17d1-0ac4-4c3c-924b-8e01d4f3124b`.

The script is in the production folder. It takes an environment name and a region, and it creates only a key, not an alias.

### 5.5 Test server role

The role `parmana-test-server` was created in the console, with trust for EC2 and no permissions policy. A later create attempt reported that the role already existed. The Terraform plan then read it. I didn't confirm which attempt created it.

### 5.6 Terraform, test stack

The test stack is `infra/parmana-test-signing`. It is a separate folder with its own local state. Its state files are gitignored (`.gitignore`).

**Plan 1, wrong folder (not applied).** The plan ran in `infra/parmana-prod-signing`. That folder's state already contained production resources: `alias/parmana-prod` and the role policy `parmana-vercel-kms-signer:parmana-prod-kms-signing`. The plan treated them as deleted and proposed changing the output to `alias/parmana-test`. Nothing was applied. The test variables file was moved to its own folder (commit `6b920c6f`).

**Plan 2, test folder.** Result: `Plan: 6 to add, 0 to change, 0 to destroy`. It planned the alias, the signing policy, the secondary KMS key, the secret, the secret policy and the secret read policy.

**Apply 1 (partial).** Created the alias, the signing policy and the secondary KMS key. Creating the secret failed:

```
creating Secrets Manager Secret (parmana-test/secondary-key): ... AccessDeniedException: Access to KMS is not allowed
```

The runner policy lacked the KMS actions needed to create a secret encrypted with the new key. The statement `TestSecretKeyUse` was added to the runner policy, with the five actions listed in §3. The apply that followed succeeded (see Apply 2 below). Whether each of the five actions was needed is not tested.

**Plan 3.** `Plan: 3 to add, 0 to change, 0 to destroy`.

**Apply 2.** `Apply complete! Resources: 3 added, 0 changed, 0 destroyed.` The secret created in this apply (ARN ending `-pJASXx`) was the secret that the key described in §5.7 was stored in.

### 5.7 Secret value, first attempt (the unknown key)

1. `npm run generate:hybrid-secondary-key` was run. It **refused**, printing `Key material already exists at "./keys" (default-secondary.private.pem / default-secondary.public.pem). Refusing to overwrite existing keys`. So the key stored next came from the existing `keys/` folder. Its origin is not known.
2. The operator ran `aws secretsmanager put-secret-value --secret-id parmana-test/secondary-key --secret-string file://keys/default-secondary.private.pem`. Result: version `22180041-1ecf-4294-a445-5bd246829568`.
3. The operator deleted `keys/default-secondary.private.pem` and `.public.pem`. The command ran without an error message.
4. **Containment:** the test secret was force-deleted with no recovery window:
   ```
   aws secretsmanager delete-secret --secret-id parmana-test/secondary-key --force-delete-without-recovery --region ap-southeast-2
   ```
   Output: `DeletionDate: 2026-11-21T06:54:15.520000+05:30`. All versions of the secret, including `22180041`, were removed.
5. The state was refreshed. `Plan: 2 to add, 1 to change, 0 to destroy`. Terraform recreated the secret.
6. `Apply complete! Resources: 2 added, 1 changed, 0 destroyed.` The new secret ARN ends `-0DVlPY`.

Whether the unknown key was a production key is **not established**. Production was not touched by any command in this run, and the copy in the test account has been removed.

### 5.8 Secret value, the key with known origin

The store script was added (`scripts/store-secondary-key.mjs`, commit `55a5aaa0`). It generates an ML-DSA-65 key in a temporary folder, checks it, stores it with `put-secret-value`, and deletes the folder even when the store fails. It never reads `keys/` and never prints key material.

```powershell
node scripts/store-secondary-key.mjs --secret-id parmana-test/secondary-key --region ap-southeast-2
```

Output:

```
Stored a new key in arn:aws:secretsmanager:ap-southeast-2:703759331191:secret:parmana-test/secondary-key-0DVlPY
Version: ecd0197e-de4b-4e99-a0ac-ff9807b134a1
```

### 5.9 Server-role read check (EC2)

1. An instance was launched in `ap-southeast-2`: Amazon Linux 2023, `t3.micro`, public IP, instance profile `parmana-test-server`, key pair `parmana-test-check`. The security group allowed SSH only from the operator's IPv4 address, `/32`. HTTP and HTTPS were not allowed. "Default AWS service access" was unticked, so no second role was created.
2. The operator connected with `ssh -i <key> ec2-user@<public IPv4>`. The first attempt failed with "Bad permissions" on the key file. The key file's permissions were fixed with `icacls` (inheritance removed, read access for the current user only).
3. On the instance:

   ```bash
   aws sts get-caller-identity --query Arn --output text
   ```

   Output: `arn:aws:sts::703759331191:assumed-role/parmana-test-server/i-05f355e07aae8b7ba`

4. On the instance, Node 24.18.0 was installed from the Node.js distribution, and the secret was read into a file, checked, and deleted:

   ```bash
   aws secretsmanager get-secret-value --secret-id parmana-test/secondary-key --region ap-southeast-2 --query SecretString --output text > key.pem
   node -e 'const c=require("crypto");console.log(c.createPrivateKey(require("fs").readFileSync("key.pem","utf8")).asymmetricKeyType)'
   shred -u key.pem
   ```

   The `get-secret-value` call succeeded. Output of the `node` line: `ml-dsa-65`.

## 8. Deviations and problems

1. **Plan in the production folder.** The first plan ran in `infra/parmana-prod-signing` with the test variables. Production resources in that folder's state were shown as deleted. Nothing was applied from that plan. The test stack was moved to its own folder (§5.6).
2. **Production folder state.** That state still lists `alias/parmana-prod` and the role policy `parmana-vercel-kms-signer:parmana-prod-kms-signing`. The production documents say the stack was never applied. This contradiction is **open** and needs the owner's check: find out how that state was produced and what the production resources are.
3. **Unknown key in the test secret.** The first stored key came from `keys/`, and its origin is not known. It was removed from the test account by force-delete (§5.7).
4. **AWS Organization in production.** During account setup, an AWS Organization (`o-rxp1wdk59h`) was created in the production account, with the production account as its management account. It has no members. The organization is not used by this run. Keep or delete it: owner decision.
5. **Missing KMS permissions.** The runner needed KMS actions for the secret's key, which weren't in the first policy (§5.6).
6. **Identity check region.** The identity script signed for the wrong region when `AWS_REGION` was set (§5.3). Fixed.
7. **Key file permissions on Windows.** SSH refused the key file until its permissions were fixed with `icacls` (§5.9).
8. **Keys on the operator's PC.** The runner's access key and the EC2 key file are still on the operator's PC (§9).
