# Summary

Parmana's consumers verify what parmana-core signs: the connect service verifies signed releases and signed authorizations, and the connectors verify signed signal queries. Today each consumer checks those formats against fixtures that were copied from core by hand, once, and are not regenerated automatically. When a consumer upgrades its `@parmana/*` packages, nothing checks that core's current output still verifies.

This RFC proposes that parmana-core publish a versioned set of conformance vectors, produced by its own signing code, and that every consumer run them in CI. It also proposes a scheduled live smoke test against a staging core, and a checked-in example of one authorized execution that the smoke test can run.

# Problem

1. **The fixtures are a snapshot.** `parmana-connect/tests/fixtures/parmana-core` was generated on 2026-10-29. The test that loads them, `parmana-connect/tests/core-fixtures.test.ts`, says "Regenerate them from parmana-core, not by hand, when the format changes", but no script in either repository does that.
2. **Major-version bumps are not verified against core.** The 27 November 2026 Dependabot PRs moved `@parmana/crypto` from 0.1.1 to 5.0.0 (connectors #94) and `@parmana/envelope-verifier` from 0.1.0 to 5.0.0 (connect #58). Both pass the local test suites, but those suites check the connectors' own output and the old fixtures. Neither was checked against a release signed by the current core.
3. **A live check needs an undocumented setup.** A local parmana-core instance (`npm run dev:setup`) refused an execution request from the dev caller because the caller is not permitted to assert the request's `principalId`. The authority grants and approval steps needed for one authorized execution are not written down anywhere a consumer can run them.
4. **The verifier already does this, and nothing else does.** The offline verifier publishes test vectors that core's signing code generated. Connect and connectors do not use them.

# Proposal

**Phase 1: vectors from core.** On each parmana-core release, a CI job runs core's signing code over fixed inputs and writes a vectors file:

- a signed release, in the form the connect service consumes;
- a signed authorization, in the form the connect bearer-token path consumes;
- a signed signal query, in the form the connectors verify;
- each with its input, its canonical bytes, its public key, and the core version and key id that produced it.

The file is published with the SDK release and is named by core version. Core's test suite checks that a regenerated file is byte-identical to the one committed for that version, so the vectors cannot drift silently.

**Phase 2: consumers run them.** Each consumer (`parmana-connect`, `parmana-connectors`) pins the vectors for the core version it targets, and its CI verifies every vector with the `@parmana/*` package versions in its own lockfile. A Dependabot PR that changes a `@parmana/*` package fails CI if it cannot verify the vectors. The fixtures copied by hand are deleted once the vectors replace them.

**Phase 3: a live smoke test.** A scheduled workflow, weekly and on demand, starts a parmana-core instance with a test authority and a test approver, makes one approved action through the documented example, and verifies the resulting release with each consumer's current packages. Failures open an issue. The smoke test does not run against production and holds no production key.

**Phase 4: the example.** Core ships one checked-in, documented example of an authorized execution, including the authority grant and the approval steps. The smoke test uses it. This is what the dev caller in problem 3 was missing.

# Non-goals

- The vectors do not prove that a connector's business action is correct. They prove that the signed bytes verify.
- The smoke test does not replace the connector's own tests, and it does not test a live institutional system.
- This RFC does not change any signature format. If a format changes, the vectors change with it, and consumers must update their pins deliberately.

# Risks

- **Vector maintenance.** Each core release adds a file. Mitigation: the file is generated by CI, not by hand, and old versions are kept.
- **Secrets.** The vector signing keys are test keys. They must never be a production key, and CI must refuse to use one. Mitigation: a separate key id that core's production config does not load.
- **Smoke test flakiness.** A live smoke test can fail for reasons unrelated to the formats. Mitigation: it opens an issue rather than blocking a release.

# Alternatives considered

- **Keep hand-copied fixtures.** Rejected: the 2026-10-29 snapshot is already stale.
- **Share one test package across repositories.** Rejected for now: it couples the consumers' release cycles to core's. The versioned vectors file keeps them independent.
- **Test only in parmana-core.** Rejected: core cannot see a consumer's lockfile, so a consumer's package bump is never checked.

# Decisions for the owner

1. Should the vectors be published with the SDK release, or as a separate artifact?
2. Which key id does the vector signer use, and where is its private key stored?
3. Should the smoke test run weekly, or on every core release?
4. Who owns the failure issues from the smoke test?
