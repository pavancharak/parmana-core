# Ed25519 signing: current state, limits, progress and next steps

Status as of 2026-11-09. This document covers Ed25519, the signature algorithm the product uses today. It is one of three
documents: `ED25519.md`, `HYBRID.md` and `ML-DSA-65.md`.

## 1. What Ed25519 is in this product

Ed25519 is the default signature algorithm. With the default settings (`CRYPTO_MODE=single`,
`PRIMARY_SIGNATURE_PROVIDER=ed25519`), every Execution Trust Record, Receipt and inbound check record is signed with it.

It is the algorithm the code is written around today:

- The local key provider (`FileKeyProvider`) reads and writes Ed25519 key pairs (`default.private.pem`,
  `default.public.pem`).
- The AWS KMS signer (`KmsSigner`) signs with `ECC_NIST_EDWARDS25519` and the `ED25519_SHA_512` algorithm, with message type
  `RAW`. Its code comment records that AWS added Ed25519 support to KMS in November 2025.
- The approval and business-source flows verify Ed25519 signatures. `approval-issuers.ts` accepts only Ed25519 public keys for
  approvers, and `HttpBusinessSignalSource` requires Ed25519 answers.
- The published verifier (`parmana-verifier`) verifies Ed25519 signatures, and so does the TypeScript and Python SDK
  verification.

## 2. Current limits

These are limits of the code as it is on `main`, not plans.

| #   | Limit                                                                                                                                            | Where it applies                                  | Effect                                                                                                                                                               |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| L1  | Ed25519 is not post-quantum. A large enough quantum computer could forge Ed25519 signatures.                                                     | All records signed in single mode with Ed25519    | Records are not protected against a future quantum break on their own. This is the reason hybrid and ML-DSA-only exist.                                              |
| L2  | KMS supports one key spec only: `ECC_NIST_EDWARDS25519`.                                                                                         | `KmsSigner`                                       | An AWS KMS deployment can use Ed25519 only.                                                                                                                          |
| L3  | KMS `RAW` messages are limited to 4 KB. Gap G-59 records a production failure from this limit under Ed25519, when records were larger than 4 KB. | `KmsSigner`, message type `RAW`                   | G-59 is recorded as the cause. I have not checked its current status in `VERIFICATION-GAPS.md`. Confirm that G-59 is closed before relying on KMS for large records. |
| L4  | Approvers and business sources must use Ed25519 keys.                                                                                            | `approval-issuers.ts`, `HttpBusinessSignalSource` | A post-quantum approver key cannot be registered today.                                                                                                              |
| L5  | The default key is named `default`. Rotation overwrites or adds key files; there is no separate rotation procedure in this document.             | `FileKeyProvider`, `PARMANA_KEY_DIR`              | Rotation has to be done carefully, because records are verified by the key ID they were signed with.                                                                 |
| L6  | Test runs use a generated Ed25519 key for the default key.                                                                                       | `vitest.setup.ts`                                 | Tests of other algorithms need the harness fixed first (see `ML-DSA-65.md`).                                                                                         |

## 3. Progress

- Ed25519 is the default in every mode. The full default test suite passes: 367 files passed, 24 skipped; 3682 tests passed,
  89 skipped (run under Node 24.22.1, after the changes in PR #541).
- The local signer and the KMS signer for Ed25519 are both in the code and tested by the unit suite.
- Ed25519 is the only algorithm that the approval, business-source and outcome-recording paths accept. This has been true
  throughout.

## 4. Next steps

1. **Confirm the status of G-59.** Check that KMS signing of records above 4 KB works, or record that it does not. This
   decides whether KMS is safe for large Execution Trust Records today.
2. **Decide the default between Ed25519, hybrid and ML-DSA-65.** Ed25519 is the default now. The post-quantum decision
   (`docs/internal/designs/POST-QUANTUM-MODE.md`) requires ML-DSA-only to be available. It does not say the default changes.
3. **Keep Ed25519 documented as the default** in `docs/site/deployment/environment-variables.mdx`, so the default matches the
   code.
